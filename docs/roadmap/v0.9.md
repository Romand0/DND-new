# 内测 v0.9 版本规划（Roadmap）

Feature Name: v0.9-roadmap
Updated: 2026-11-27
前序版本：`docs/changelog.md` 内测 v0.8（已收束，main `b76633f` 起）

## 一、版本目标

v0.8 完成「战斗引擎全套」。v0.9 的主题是**跑团全流程闭环**：把 AI 生成能力嵌进站点、让剧情内容成为一等数据、用圆桌与通知把 DM↔玩家协作补齐，并清理战斗系统残留。

版本验收的总口径：DM 在站点内可以完成「准备剧情 → 派发任务 → 抛送检定 → 开战 → 结算 → 玩家查看回顾」的完整链路，不依赖站外工具。

## 二、任务总览

| 编号 | 任务 | 优先级 | 规模 | 依赖 | 状态 |
|------|------|--------|------|------|------|

| V9-2 | 剧情全周期管理（**重点**） | P0 | XL | 团组作用域、日历/游戏时间、圆桌/日志/宝藏/审批 | 已立项（`story-management`，P1 待开工） |
| V9-3 | 圆桌功能与 UI 落实 | P1 | L | M-R1 信箱（已交付） | 未开工 |

建议节奏：V9-2 主线先立项（P0），V9-5 作为穿插任务随时消化，V9-1 与 V9-3 并行推进，V9-4 在 V9-3 任务卡落地后接入。

## 三、V9-1 Cloudflare Workers 嵌入 + 法术批量流水线

### 现状

- `flow-ai-generation`：prompt 资产层与 Workers AI 实验脚本已合入；P2（实验执行）卡在 CF 凭据，P3（生成端点 `functions/api/flows/generate.ts`）、P4（FlowEditor AI 入口）未做
- `spell-flow-pipeline`：requirements / design 在档，仍依赖 agent skill + 人工粘贴，无站点内执行链路
- 数据规模：`spells-import/` 共 360 条法术待流程化；`functions/api/flows/batch/index.ts` 已有批量入库端点（人工 JSON）
- `wrangler.toml` 未声明 `[ai]` binding

### 目标

DM 在站点内选择法术（单条或批量），Workers AI 生成 FlowScript，服务端校验 + 重试，产出草稿进入人工审核队列，审核通过后走既有 batch 入库。agent skill 流水线降级为离线兜底与 prompt 维护来源。

### 分期

| 阶段 | 内容 | 产物 |
|------|------|------|
| P1 | Workers AI 接入：`wrangler.toml` 加 `[ai]` binding；`functions/api/flows/generate.ts`（admin JWT → 模型调用 → 校验重试环，不落库）；补齐 flow-ai-generation P2 实验结论 | 生成端点 |
| P2 | 前端单条入口：FlowEditor「AI 生成」→ 草稿预览 → 人工确认入库 | 单条闭环 |
| P3 | 批量任务：选法术集合（按环阶/关键词）→ 排队生成（串行限流 + 断点续跑）→ 草稿审核列表（通过/驳回/重试） | 批量工作台 |
| P4 | 与 spell-flow-pipeline 融合：法术原文检索（站内法术库 + 不全书离线包）→ prompt 装配复用流程生成器资产；成本/失败率/耗时审计面板 | 线性流水线 |

### 不做

- 不做模型微调与自建推理
- 不自动发布：所有生成结果必须经人工审核入库（沿用「生成器不自行发布」原则）
- 不在本轮做多模型路由

### 验收

- 单条：输入法术 → 生成合法 FlowScript（`ensureCompiledGraph` 通过）→ 人工确认后可发布
- 批量：一次投 20 条，任务可中断续跑，失败条目有原因与重试按钮，无重复入库
- 审计：每次生成记录模型、耗时、token/费用估算、校验重试次数

### 风险

- Workers AI 模型对长文本的 JSON 稳定性有限 → 必须保留服务端校验 + 有限重试 + 失败降级人工
- 批量生成成本与速率限制 → 串行队列 + 每日配额

## 四、V9-2 剧情全周期管理（重点任务）

### 现状

- 站点无剧情数据模型：`NotesPage.tsx` 只是时间/日历/信箱汇总页，不是剧情管理
- 团组（Campaign）已是顶层容器，有成员/角色卡/规则书/战斗/宝藏
- 圆桌信箱已有 campaignId 作用域与可见性先例（任务指派 = 单角色可见）
- 日历与游戏时间已存在（`calendarStore` / `gameTimeStore`），尚未与剧情事件联动
- 经济事件已分散落地：`character_logs`（物资/施法/成长）、圆桌检定消息、宝藏分配、变更审批

### 定位

模块由两个域组成，共用「剧情线 → 章节 → 场景」骨架：

- **剧情笔记域（DM 私有）**：DM 导入既有剧情文本，组合片段、引用规则实体、写私记，并提供 DM 阅读视图。讲述与扮演由 DM 现场完成，玩家端不呈现叙事文本。
- **战役经济账本域**：以场景为挂载点，汇总检定、物资、宝藏、施法、成长五类经济事件。源记录保持权威，模块只存索引引用，读取时聚合。

与玩家的互动落在经济层：抛送检定、派发任务、分配宝藏、交易与物资变动、施法申报，复用既有圆桌与战斗链路。玩家端额外接收道具型文本（信件/地图/告示）。

### 已定稿决策（2026-11-27）

| 决策点 | 结论 |
|--------|------|
| 模块定位 | 双域：DM 剧情笔记 + 战役经济账本（页面与真实目标保留 `story-management`） |
| 备注文本 | 仅 DM 侧组合与呈现；不做面向玩家的剧情阅读器 |
| 投送范围 | 经济交互 + 道具型文本（`letter`/`map`/`notice`/`other`），不作叙事载体 |
| 账本来源 | 汇总引用既有权威记录（角色日志/检定消息/宝藏/变更请求），不建统一事件表、不双写快照 |
| 单元粒度 | 场景（StoryScene）为经济事件挂载点，五轴齐全 |
| 奖励语义 | 计划 + 实际双轨；实际奖励只存宝藏引用，分配明细以宝藏模块为权威 |
| 时间语义 | 游戏内时间 / 跑团场次 / 剧情顺序三字段并存，均可空，`order` 必填 |
| 团队语义 | 长期团队（团组绑定角色）+ 当场在场名单（角色/NPC/缺席）两层 |
| 存储 | 剧情树复用 `campaign_artifacts`（`kind='story'`，一弧一行）；索引/道具/已读走 migration 0017 |
| 权限 | DM 写笔记、索引与道具；玩家读自己角色的经济事件与目标道具；笔记对玩家投影为空 |

详细数据模型、账本聚合、API、投影与正确性属性见 `.monkeycode/specs/story-management/design.md`。

### 数据模型摘要

```
StoryArc（剧情线，campaign 作用域）
 └─ StoryChapter（章节，order）
      └─ StoryScene（场景 = 一段剧情 + 账本挂载点）
           ├─ 时间：gameDate/gameMinute + sessionNo + order
           ├─ 空间：location{name, region?, battlegroundId?}
           ├─ 团队：roster{characterIds, npcIds, absentCharacterIds}
           ├─ 笔记：snippets[]（组合片段 + 实体引用）/ dmNotes（私记）
           ├─ 计划：plannedObjectives[] / plannedReward{currency,items,experience}
           └─ 支撑：status / dependsOn / resultNotes / settlementSummary / combatRecordId

StoryLedgerLink（账本索引，只存引用）
 └─ sourceKind(check|item|treasure|spell|growth) / sourceId / characterId / occurredAt / note

StoryHandout（道具投送）+ StoryHandoutRead（每人已读/收藏）
```

### 分期

| 阶段 | 内容 |
|------|------|
| P1 | 笔记域数据层：类型 + `_shared.ts` 校验/投影 + `/api/story` 读写 + frontend store + 探针 |
| P2 | 账本域：migration 0017 + 索引 CRUD + 五类源聚合端点（角色过滤、失效引用）+ 宝藏分配补写角色日志 + 探针 |
| P3 | DM 工作台 `/story`：剧情线/章节/场景编辑；既有文本导入与片段组合；装备/法术/怪物引用；DM 阅读视图；账本候选挂载与时间线 |
| P4 | 道具投送 + 玩家端道具箱 + 玩家自己的经济事件视图 |
| P5 | 场景结算摘要、按场次/时间/角色筛选、Markdown 导出 |

### 不做

- 不做面向玩家的剧情文本与叙事阅读器
- 不做讲述、扮演、语音与虚拟形象
- 不做 AI 自动生成或续写剧情（V9-1 之后独立探索）
- 不做多人同时编辑同一剧情线
- 不迁移历史笔记与战斗数据进剧情模型
- 不替代既有检定、战斗、宝藏、经济模块（本模块只做索引与聚合）

### 验收

- DM 能导入既有剧情文本并切成场景草稿，组合片段、写私记，在 DM 阅读视图按章节顺序浏览
- 玩家请求剧情接口时拿不到任何场景文本、私记、计划奖励与场景状态（接口层裁剪，非前端隐藏）
- 场景内可挂载检定/物资/宝藏/施法/成长五类事件，账本按时间线展示，数值与源模块一致
- 源记录删除后索引保留并标记失效，DM 可手工解除
- DM 可发信件/地图/告示给指定玩家，玩家端道具箱显示已读/收藏，零已读时可撤回
- 场景完成生成结算摘要；可按场次、游戏内时间、角色筛选回顾

### 风险

- 索引与源记录双读的一致性：读取时聚合、缺失标失效；探针覆盖失效与越权
- 权限过滤是核心正确性：笔记、账本、道具三条读取路径都要探针覆盖
- 数据量增长后的加载策略：按剧情线懒加载章节/场景，不分页整树

## 五、V9-3 圆桌功能与 UI 落实

### 现状

- `round-table-hub` roadmap 的 M-R1（通用检定）、M-R2（战斗观战抛送）已交付
- 圆桌桌面（M-R3a）已交付：`/table` 首屏环形展示团组成员头像，拖拽/点选检定投递物即选中目标角色；记录区已按待处理/检定/观战/裁定分类折叠，观战同房间投送合并，收纳区每页 5 条分页；任务、物资投递为规划中占位
- `/player/table`（玩家）仍是消息列表形态；DM 端也未做三区枢纽布局
- M-R3（枢纽页 + 全站搜索阶段一）、M-R4（任务插件）、M-R5（成长任务）、M-R6（搜索阶段二）未开工

### 目标

把圆桌从「消息列表」升级为枢纽页：以环形成员桌面为第一屏（投递目标选择器），叠加任务流 + 搜索 + 跳转卡三区，并把 M-R4/R5 的任务插件与成长任务链路落地。

### 分期

| 阶段 | 内容 | 对应里程碑 |
|------|------|-----------|
| P1 | 圆桌桌面（已交付）+ 三区布局 + 跳转卡（绑定角色/图鉴入口/进行中战斗/待办角标） | M-R3a / M-R3 前半 |
| P2 | 全站搜索阶段一：provider 注册模式 + 玩家三库 + DM NPC 模板，前端内存索引与相关度排序 | M-R3 后半 |
| P3 | 任务插件：`task` 消息类型 + 任务状态机（open/in_progress/done/cancelled/review/rejected）+ 剧情任务派发/完成 + 检定消息聚合 | M-R4 |
| P4 | 成长任务：升级触发 → 选法术/特性/属性提升 → DM 审核 diff → 落卡 | M-R5 |
| P5 | 搜索阶段二（D1 FTS5 / 服务端相关度）与 provider 扩展 | M-R6 |

### 不做

- 不做实时推送（本轮仍用轮询游标；DO 推送另立项）
- 不做跨团组全局搜索（搜索范围限定当前团组 + 公共库）

### 验收

- 玩家进入圆桌第一眼能看到围坐的团组成员，以及「待办任务数 / 未读邀请 / 角色卡入口」
- DM 把「检定」投递物拖到成员头像后，发起表单的目标角色自动选中该成员绑定角色
- 搜索「火球」命中火球术并可按描述关键词命中，玩家搜不到 NPC 模板
- 剧情任务可派发到单角色，玩家标记完成，DM 确认后关闭
- 成长任务全链路：升级 → 玩家选取 → DM 审核 → 角色卡字段正确更新

### 风险

- 任务状态机与既有检定 `status` 字段兼容：检定消息不迁移，任务卡只读聚合
- 搜索权限必须服务端过滤，前端索引只是缓存

## 六、V9-4 通知系统

### 现状

- 无通知基础设施；用户只能靠主动打开圆桌查看待办
- 已有可复用事件源：检定请求/结果、决策点、观战邀请、变更审批（`change-requests`）、角色成长任务（V9-3）
- 圆桌信箱已有游标增量模型（`id > lastSeenId`）

### 目标

站内通知中心：所有需要用户处理或知悉的事件统一进入通知流，铃铛角标显示未读数，支持已读与跳转。通知是**索引层**，不复制消息体。

### 分期

| 阶段 | 内容 |
|------|------|
| P1 | 通知事件模型 + `notifications` 表（migration）或由事件源派生 + 未读游标（复用 lastSeenId 思路） |
| P2 | 铃铛 UI + 通知中心（分组/过滤/已读/全部已读）+ 角标 |
| P3 | 事件接入：检定请求、战斗邀请、变更审批结果、任务指派（V9-3）、道具投送（V9-2） |
| P4 | 可选外部通道：Web Push / 邮件（需用户授权与 CF 侧配置，默认关闭） |

### 不做

- 不做短信与第三方 IM 集成
- 不做通知偏好设置矩阵（首版只做总开关 + 分类静音）

### 验收

- DM 抛送检定后玩家 30 秒内（轮询周期）看到角标
- 点击通知跳到对应页面并定位到具体条目
- 已读状态跨设备一致（服务端游标）
- 不产生重复通知（同一事件只入一次）

### 风险

- 通知与信箱双写一致性：优先派生，避免两套状态；确需落表时以事件 ID 幂等
- 轮询开销：合并请求（一个接口返回计数 + 最近 N 条）

## 八、跨任务统一约束

1. **玩家永不直写角色卡**：剧情揭晓、任务完成、成长选取都经 DM 审核落卡
2. **权限过滤在服务端**：剧情笔记（玩家侧投影为空）、账本（按绑定角色）、道具（按目标）、搜索 provider、通知事件均按请求者裁剪
3. **消息不可变**：圆桌请求/回执维持现有模型；任务实体可独立建表，但状态回填只碰状态字段
4. **本地存储 + 云同步**：新 store 遵循 8 件套；新表结构走追加式 migration（本版本预计 0017 起）
5. **验证口径**：数据级探针 + 人工 UI 验收；探针前冷重启 dev server

## 九、待决策（开工前需确认）

1. **V9-1**：批量生成的每日配额与预算上限？失败条目自动重试次数（建议 2 次）？
2. **V9-3**：任务插件先做「剧情任务」还是直接做「成长任务」？（建议先剧情任务，成长任务涉及角色卡写权限，复杂度更高）
