# 圆桌枢纽规划（Round Table Hub Roadmap）

Feature Name: round-table-hub
Updated: 2026-11-08
Related Specs: `.monkeycode/specs/round-table-checks/`（通用检定，已交付）

## 一、定位与设计初衷

「圆桌」是提供给玩家的**枢纽类网页**：围绕最核心的游戏内容，让玩家方便地开展各类活动。比喻现实跑团桌——DM 与玩家围坐的地方，剧情材料、规则交互、个人事务都在这张桌上展开。

圆桌由三大功能域构成，共用同一套传输与权限底座：

```
┌─────────────────────────────────────────────────────┐
│  圆桌（玩家枢纽页 /player/table · DM 端 /table）      │
├──────────────┬──────────────────┬───────────────────┤
│ ① 任务管理    │ ② 全站搜索        │ ③ 跳转            │
│ 任务插件：    │ 覆盖多库：        │ 快捷入口：         │
│ 剧情/检定/   │ 名称+属性+描述    │ 角色卡 / 图鉴 /    │
│ 角色成长     │ 相关度排序        │ 加入战斗抛送       │
├──────────────┴──────────────────┴───────────────────┤
│  底座：D1 信箱（消息不可变 + 游标增量 + type 开放）    │
│  权限：账号绑定 + 站点角色（玩家三库 / DM 四库起）     │
└─────────────────────────────────────────────────────┘
```

## 二、已交付里程碑（收编）

| 里程碑 | 内容 | 交付物 |
|--------|------|--------|
| M-R1 | 通用检定：DM 定向抛送属性/技能/豁免检定，玩家投骰经特性引擎加工回传，DC 三档可见性 | `round-table-checks` spec 全量：`/table`、`/player/table`、`checkPipeline`、`table_messages` 单表信箱 |
| M-R2 | 战斗抛送加入：DM 开战时向圆桌抛送观战邀请（`?room=combat-xxx`），玩家点击即入实时观战 | PlayerSpectate 自动加入 + PlayerRoundTable 邀请卡 |

信箱模型已验证的三条架构原则，后续功能域继续遵守：

1. **消息不可变**：请求与结果是两条独立消息，状态回填仅限 status / reply_message_id 两个字段
2. **游标增量**：`id > lastSeenId` 拉取，断线重连不丢不重；传输层可替换（未来换 DO 推送仅改拉取方式）
3. **type 开放**：消息种类由 type 字段区分，新功能注册新 type 即接入同一通道

## 三、功能域一：任务管理

### 愿景

通过一个**任务插件**管理圆桌上的所有任务。「任务」的边界刻意放宽——一切「DM 与玩家之间需要被处理、被回应、被推进的事」都是任务：

| 任务类别 | 来源 | 例子 | 状态流转 |
|----------|------|------|----------|
| 剧情任务 | DM 手动派发 | 「调查酒馆地下室」「下周前来确定装备清单」 | 待处理 → 进行中 → 已完成 / 已取消 |
| 检定任务 | DM 抛送（已实现） | 属性/技能/豁免检定请求 | pending → answered / cancelled（现状态机收编为任务状态机子集） |
| 角色成长任务 | 系统触发（升级等事件） | 「升到 5 级：选取法术」「选取职业特性」「分配属性提升」 | 待处理 → 玩家填写 → DM 审核 → 合并落卡 / 退回重填 |

### 设计要点

- **统一任务卡**：任务在圆桌消息流中是一张任务卡（type=`task`），携带 `taskKind`（plot/check/levelup/…）；检定请求在任务列表中以只读摘要形式聚合展示（点击跳转检定详情），底层消息保持现有 check_request 不变
- **任务状态机**：`open → in_progress → done / cancelled`，外加 `review`（成长任务独有：玩家已填，等 DM 审核）与 `rejected`（退回重填，回到 in_progress）
- **成长任务与角色卡联动**（关键流程，也是权限敏感点）：
  1. 系统触发：DM 标记角色升级（或升级工具触发）→ 自动为该绑定玩家生成成长任务（含「选法术」「选特性」「属性提升」等子项清单）
  2. 玩家填写：任务卡内嵌选取表单（法术从法术库选、特性从职业特性清单选）——**只写任务 payload，不直接改角色卡**
  3. DM 审核：DM 端显示玩家提交的变更 diff → 通过则由 DM 端落角色卡（沿用「站点管理员有写权限」模型）→ 任务 done；退回则附理由，任务回 in_progress
  - 该流程复用「战斗场景一切变更等结算再并入角色卡」的同类思想：玩家提交的是**变更意图**，落卡永远经 DM 手
- **任务持久性**：任务与检定消息同存 `table_messages`（type=task），或独立 `table_tasks` 表（若任务需要子项清单/多字段编辑，单条不可变消息不够时拆表）。规划倾向：**任务主体独立建表 + 状态回填**，任务过程中的玩家填写内容作为不可变提交记录追加（与检定 request/result 同构）

### 验收基准（M-R4 / M-R5 展开时细化为 EARS）

- DM 可创建剧情任务并指派给单个/多个绑定角色；玩家圆桌看到任务卡并可标记完成（DM 确认）或留言
- 升级触发后，绑定玩家在其圆桌自动收到成长任务；玩家完成选取提交；DM 审核通过后角色卡对应字段更新（法术列表追加、特性追加、属性提升落点正确）
- 检定消息在任务列表中可见、可跳转，旧消息不迁移不破坏

## 四、功能域二：全站搜索

### 愿景

一个覆盖多库的统一搜索框，直接放在圆桌枢纽页。DM 与玩家的可见范围不同，但体验一致：

| 角色 | 可搜库 | 备注 |
|------|--------|------|
| 玩家 | 装备库、法术库、角色选项库 | 与玩家端只读页面的可见范围一致 |
| DM | 上述三库 + NPC 模板库 | 后续接入模组库等新数据源 |

### 特征

1. **覆盖深度**：搜索命中范围包括条目的**名称、属性字段、描述正文**——「穿刺」「 concentrates 」「恢复生命」这类正文关键词都能命中条目
2. **相关度排序**：名称命中 > 属性/关键词字段命中 > 描述命中；多关键词按命中数与字段权重加权；同分按名称长度/使用频率微调
3. **权限过滤**：同一搜索引擎按请求者角色过滤数据源；玩家搜索结果与玩家端各库页面可见范围严格一致

### 技术路线（分两阶段）

- **阶段一（前端内存索引）**：库条目量级在数百条，玩家端进入圆桌页时按需拉取可见库（装备/法术/选项已有只读 API），在前端建倒排/子串索引；搜索零后端改动、零延迟，相关度权重前端可调
  - 数据源盘点：装备/法术走 D1 API（`/api/equipments`、`/api/spells` 已有 GET 列表）；角色选项与 NPC 模板的数据源在实施前确认（NPC 模板有 D1 表与 API；角色选项若为静态数据则打包进索引）
- **阶段二（服务端检索）**：库规模增长（模组接入、条目破千）后迁移到 D1 FTS5（SQLite 全文检索，D1 原生支持）或 LIKE + 多字段权重的服务端查询；前端 provider 接口不变
- **Provider 注册模式**：每个可搜数据源实现一个搜索 provider（`{ id, label, fetchIndex(), search(query) → hits[] }`），圆桌搜索框聚合全部已注册 provider——模组等新库接入时注册新 provider 即可，搜索 UI 零改动

### 验收基准（M-R3 / M-R6 展开时细化）

- 玩家在圆桌搜索「火球」能命中「火球术」且能按描述关键词（如「球状爆炸」）命中；结果按相关度排序，显示来源库与关键命中片段
- DM 额外能搜到 NPC 模板；玩家搜索结果中不出现任何玩家不可见数据
- 搜索结果点击可跳转对应条目详情页（装备/法术详情、NPC 图鉴）

## 五、功能域三：跳转

### 愿景

圆桌作为枢纽，玩家的一切高频去向都应一步可达：

| 去向 | 形态 | 状态 |
|------|------|------|
| 我的角色卡 | 绑定角色列表 → 每个角色一张快捷卡（头像/名字/职业等级），点击进 `/player/:id` 只读卡 | 规划中（绑定数据 API 已有：`bound-characters`） |
| 翻阅图鉴 | 装备/法术/（NPC）库入口；与全站搜索互补（浏览 vs 检索） | 规划中（库页面已有，补入口卡片） |
| 加入战斗抛送 | DM 开战抛送邀请卡，点击进实时观战 | 已交付（M-R2），收编为活动卡片的一种 |

### 设计要点

- 跳转区是**动态的**：有多个绑定角色则显示多张卡；有进行中的战斗邀请则置顶；有待办任务则显示角标数字——枢纽页的信息密度服务于「玩家打开圆桌第一眼知道现在该干什么」
- DM 端 `/table` 跳转区对应 DM 视角：快捷创建检定/任务、进入战斗记录、打开账号绑定管理

## 六、里程碑路线

| 里程碑 | 内容 | 依赖 |
|--------|------|------|
| M-R1（已交付） | 通用检定 + 信箱底座 | — |
| M-R2（已交付） | 战斗观战抛送加入 | M-R1 信箱 |
| **M-R3** | 枢纽页改版：三区布局（任务流 / 搜索框 / 跳转卡）+ 全站搜索阶段一（前端索引，玩家三库 + DM NPC 模板） | 库列表 API（已有） |
| **M-R4** | 任务插件：任务卡 type 接入 + 任务状态机 + 剧情任务派发/完成 + 检定消息聚合展示 | 信箱底座 |
| **M-R5** | 角色成长任务：升级触发 + 选取表单（法术/特性/属性提升）+ DM 审核 diff + 落卡 | M-R4 + 角色卡写权限（已有） |
| **M-R6** | 搜索阶段二（FTS5 / 服务端相关度）+ provider 生态（模组库等新数据源接入） | M-R3 |

每个里程碑实施前，在本目录按惯例展开独立 spec（requirements.md / design.md / tasklist.md），命名建议 `round-table-tasks`（M-R4+R5）、`round-table-search`（M-R3+R6）。

## 七、跨里程碑架构约束

1. **信箱语义优先**：一切 DM↔玩家交互先考虑能否表达为「不可变消息 + 状态机」；确需富编辑（成长任务表单）再独立建表，保持请求/回执消息模式
2. **玩家永不直写角色卡**：检定回填、任务完成、成长选取，最终落卡动作都在 DM 端权限下发生
3. **权限过滤在服务端**：搜索 provider 的数据范围由服务端接口决定（玩家 token 只能拉到玩家可见库），前端索引只是缓存
4. **投影公开语义延续**：圆桌与观战共用「真实桌面看得见的才投」原则；任务描述、检定内容对相关玩家可见，不跨玩家泄露未公开剧情任务（任务指派粒度 = 单角色，未指派者不可见）
