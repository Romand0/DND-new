# Requirements Document：技能全周期引擎（skill-fullcycle-engine）

Feature Name: skill-fullcycle-engine
Updated: 2026-11-18
状态：定稿 v1（决策记录 2026-11-18）

## Introduction

将特性/技能的战斗接入从「经济系统 + DM 手动结算」升级为「全周期自动化」。核心动机：DM 与玩家操作是异步的（玩家打包上传 → DM 审批），玩家操作时一切数值必须静态可得；任何依赖 DM 事后手动补算的效果都会让玩家决策缺信息、DM 审批来回对账。

三层接入方针（用户拍板 2026-11-17）：越是复杂难复用的技能，越要硬编码。
- **层 A 被动技能**：全部全周期硬编码入库——「引擎」是可复用的自动处理器，零操作窗口。
- **层 B 主动技能**：按高重合度结算模式细分，开发全套功能引擎；高复用类型配套「数据提取器」（点击式从描述文本提取数值填入引擎）；难以复用的技能全周期硬编码（专用引擎 + 专用弹窗）。
- **层 C 开放效果分流**：战斗内效果开放/半开放的技能按可接入度处理——可拆形态的映射既有引擎，难复用的 P5 硬编码候选，效果任意的标记范围外。

现状基线（2026-11-18 调查，294 个 PHB2014 特性名）：层 1 全自动 6 名 / 引擎已备需手动 44 名 / 未接入 244 名（其中被动数值类约 156 名、设定类 112 名）。

## Glossary

- **全周期**：玩家端静态预览 → 操作打包 → DM 审批入账 → 效果自动落地 → 记录行完整，全程无 DM 手动补算。
- **处理器（processor）**：被动技能的自动生效单元，读角色卡特性名+参数表输出派生值（豁免优势/抗性/AC 等），无 UI。
- **功能引擎（engine）**：主动技能的结算模式实现，接受 spec 配置，输出确定性的结算结果（扣资源、掷骰/应用效果、写记录）。
- **数据提取器（extractor）**：点击式工具组件，从特性描述文本按预置正则集提取数值（骰式/DC/伤害类型/恢复量/范围），预填 spec 表单，人工确认后写入云端配置。
- **spec**：引擎配置数据（JSON），描述一个特性如何结算；区别于代码硬编码。
- **专用硬编码**：代码内注册表条目（featureCapabilities.ts），效果逻辑无法用 spec 表达时使用。
- **裁定型**：效果开放、文本主导、无结构化数值可提取的技能（如神圣干预）。

## Requirements

### R1 被动技能全周期处理器化

**User Story:** AS DM/玩家，我希望被动技能在战斗中零操作自动生效，so that 任何人都不需要记住或手动触发被动效果。

#### Acceptance Criteria

1. WHEN 战斗开始快照建立，system SHALL 按被动配置表自动派生全部命中条目（抗性/豁免优劣势/AC/速度/被动检定/黑暗视觉/先攻七类，复用 passive-engine 冻结口径）。
2. WHEN 被动配置表新增条目，system SHALL 在下一次战斗快照生效，无需代码改动。
3. WHILE 角色卡携带被动技能，system SHALL 在角色卡特性区展示「已接入：处理器类型」徽标（用户可感知接入状态）。
4. IF 描述文本含被动语义但未接入配置，system SHALL 在角色卡特性区标记「未接入」，并列出建议处理器类型（提取器入口）。

### R2 主动技能功能引擎全覆盖

**User Story:** AS 玩家，我希望发动主动技能时立即看到效果数值（消耗/伤害/恢复/DC），so that 异步提交前我的回合决策有完整信息。

#### Acceptance Criteria

1. WHEN 玩家在回合面板选择引擎化技能，system SHALL 本地按 spec 静态计算并展示：资源消耗、效果数值（骰式+固定+系数）、豁免 DC（若有）。
2. WHEN 玩家提交 feature-use op，system SHALL 打包完整结算参数（spec 引用 + 玩家填写的骰值/目标），DM 审批入账时 turnCommitApply 自动落地，DM 零手填。
3. WHEN 引擎结算完成，system SHALL 写记录行：效果明细（目标、骰值、总量、DC 对比）与资源扣减。
4. IF spec 缺失或解析失败，system SHALL 降级为 manual 兜底（现有行为），并在玩家端标记「未接入」。

### R3 数据提取器

**User Story:** AS DM，我希望通过简单点击从特性描述中提取数值并填入引擎，so that 不需要懂代码就能把技能接入自动化。

#### Acceptance Criteria

1. WHEN DM 在特性编辑界面点「接入引擎」，system SHALL 展示引擎类型选择器（按描述关键词预推荐）。
2. WHEN 引擎类型选定，system SHALL 按类型跑预置正则集提取描述文本，高亮命中片段并预填 spec 表单。
3. WHEN DM 确认提交，system SHALL 校验 spec 合法性（引擎 schema）后写入云端配置，并立即生效。
4. IF 提取置信度低（命中缺失/多义），system SHALL 逐项标记「需人工确认」，禁止静默填默认值。
5. WHEN 对种子库运行批量提取，system SHALL 输出逐条预填报告（成功/低置信/失败），失败项可人工补录。

### R4 专用硬编码通道

**User Story:** AS 开发者，我希望复杂技能走专用引擎+专用弹窗全周期硬编码，so that 效果逻辑清晰且复用性差的设计开销可控。

#### Acceptance Criteria

1. WHEN 技能效果含多效应组合/特殊时点/专用交互 UI，system SHALL 走专用硬编码（代码注册表条目 + 专用结算组件），a oe_save（吐息武器）为参照模式。
2. WHEN 专用硬编码技能发动，system SHALL 与 spec 引擎共享同一经济漏斗（池扣/动作扣/记录行），仅结算段差异化。
3. IF 通用引擎 spec 无法表达某技能，system SHALL 保留其 manual 兜底并在配置界面标注「建议硬编码立项」。

### R5 配置数据层与解析顺序

**User Story:** AS 开发者，我希望引擎配置存云端并按确定顺序解析，so that 玩家端与 DM 端拿到同一份配置且专用硬编码可覆盖。

#### Acceptance Criteria

1. WHEN resolveFeatureCapability 解析特性，system SHALL 按「代码注册表 → 云端配置 → manual 兜底」顺序返回能力。
2. WHEN 云端配置与代码注册表同名冲突，system SHALL 以代码注册表优先（专用硬编码覆盖通用配置）。
3. WHEN 玩家端/DM 端加载战斗页面，system SHALL 获取作用域内配置集（含种子预填），离线/失败时回退代码注册表并提示。

### R6 战斗内开放效果技能的处理（决策记录 2026-11-18）

**User Story:** AS 开发者，我希望战斗内效果开放的技能按可接入度分流，so that 战斗攻坚阶段资源集中在可结构化的能力上。

项目定位修正（用户拍板）：本站是**线下 DND 工具**，战斗系统攻坚阶段不处理「效果任意」的裁定队列机制。

#### Acceptance Criteria

1. WHEN 引导神力接入，system SHALL 拆为 4 个子形态分别映射引擎（生命→B3 heal、毁灭→B4 rider、不灭信念→B8 reaction、光辉→B5 aoe_save），容器特性按选择弹窗分流。
2. WHEN 荒野变形立项，system SHALL 走专用硬编码评估（变身=参战者数据替换引擎，P5 候选）。
3. IF 技能效果任意且战斗内出现（神圣干预），system SHALL 标记「裁定型·另议」，本轮范围外。
4. IF 技能属于休整期/非战斗机制（奥术回想/魔能掌控），system SHALL 标记「非战斗·后置」，本轮范围外。

### R7 迁移与兼容

**User Story:** AS 开发者，我希望现有 6 条硬编码注册与种子标注平滑平移，so that 已验收行为零回归。

#### Acceptance Criteria

1. WHEN 新数据层上线，system SHALL 保持现有 6 条代码注册条目行为不变（探针 1-13 段全绿）。
2. WHEN 种子标注（36 显式条目）接入新配置层，system SHALL 由提取器跑批产出预填 spec，原五字段标注保留兼容。
3. IF 老角色卡特性无任何配置，system SHALL 维持现有行为（按钮 + manual 提示）作为最终兜底。

## 决策记录（2026-11-18 定稿）

1. **配置作用域**：站点默认 + 团组覆盖。configs 表 `scope` 字段区分（`'site'` / campaign id），解析时团组覆盖同名站点条目。
2. **裁定型分流**（R6）：引导神力拆形态接入既有引擎；荒野变形 P5 硬编码候选；神圣干预（效果任意）本轮范围外另议；奥术回想/魔能掌控非战斗后置。裁定队列机制本轮不建。
3. **骰值归属**：玩家端掷（或按现状填值），结果随 op 提交，DM 入账直接采用。理由：线下工具定位，与 attack d20 玩家填值先例一致；DM 审批零额外操作。
